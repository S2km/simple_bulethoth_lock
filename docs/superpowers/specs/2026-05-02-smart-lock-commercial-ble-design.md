## Goal

Turn the current STM32 + HC-04BLE + WeChat Mini Program lock prototype into a stricter first-release product baseline with:

1. authenticated lock control,
2. configurable automatic relock,
3. remembered auto reconnect,
4. trusted multi-phone support,
5. optional saved PIN and optional background auto-auth,
6. RSSI-based proximity auto unlock with anti-false-trigger rules,
7. persistent settings that survive power loss and restart.

This phase focuses on a strong local BLE product loop. It does not add cloud accounts, remote control over the Internet, or a backend service.

## Current Context

- The firmware already accepts BLE/UART text commands and controls the servo.
- The Mini Program already supports BLE scan, connect, characteristic discovery, log output, auth countdown, and lock/unlock actions.
- The current authentication model is still a single fixed PIN in firmware.
- The current persistence model does not yet support durable PIN updates or trusted-phone records.
- The current Mini Program remembers the last successful device for reconnect, but it does not yet implement trusted-phone binding, per-phone settings, proximity unlock, or product-grade settings management.

## Product Decisions Confirmed

The product behavior for this phase is fixed as follows:

- BLE remains the only local control transport.
- A global lock PIN exists and can be changed from the Mini Program.
- The changed PIN must survive power loss and reboot.
- Auto relock is enabled and configurable to `3 / 5 / 8 / 10 seconds`.
- Default auto relock is `5 seconds`.
- Proximity unlock is allowed, but only through a guarded flow.
- Auto-auth using a saved PIN is optional and controlled by a Mini Program switch.
- Successful prior connection enables remembered auto reconnect behavior.
- Multiple phones are supported.
- The recommended multi-phone model is `global PIN + trusted phone whitelist`.
- Unbound phones may still perform manual one-time access by entering the current PIN, but they cannot use trusted automatic convenience flows.

## Recommended Product Model

Use two access lanes:

1. **Manual access lane**
   - Any phone that can connect may enter the current PIN.
   - After successful manual auth, that phone can manually lock/unlock during the short auth window.
   - This lane supports temporary use and onboarding.

2. **Trusted-phone lane**
   - A phone must first be bound into the lock whitelist.
   - That phone receives a durable `clientId`.
   - Only trusted phones may use saved-PIN auto-auth and proximity auto unlock.
   - Removing a trusted phone disables its automatic convenience path.

This model keeps the product practical while avoiding the weight of a full user-account system.

## Architecture Summary

### Firmware Responsibilities

The firmware owns:

- the lock actuator state,
- the auth timer,
- wrong-PIN lockout,
- durable PIN storage,
- durable auto-relock storage,
- trusted-phone records,
- protocol validation,
- safe default recovery after invalid persisted config,
- final relock execution.

### Mini Program Responsibilities

The Mini Program owns:

- BLE reconnect and scan UX,
- local remembered device metadata,
- local remembered PIN option,
- trusted-phone binding UX,
- per-phone convenience switches,
- RSSI observation and proximity decision logic,
- command orchestration,
- product logs and settings UI.

### Why the relock must live in firmware

Automatic relock must not depend only on the phone, because:

- the phone may disconnect after sending `UNLOCK`,
- the app may be backgrounded,
- BLE may flap,
- the user explicitly wants a product that is less likely to fail later.

The app may still show relock countdown state, but firmware is the source of truth for relock execution.

## Identity and Binding Model

### Lock-level Identity

The lock has:

- one global PIN,
- one auto-relock setting,
- up to `5` trusted phone records.

### Trusted Phone Record

Each trusted phone record contains at minimum:

- `clientId`
- `nickname`
- `enabled`

Recommended format:

- `clientId`: `16` to `32` uppercase hex characters generated by the Mini Program once and reused for that phone on that lock.
- `nickname`: short printable label shown in the Mini Program trusted-phone list.

The lock does **not** need to persist phone-local RSSI thresholds to make the first release work safely. RSSI thresholds are better treated as per-phone local tuning values in the Mini Program. The lock only needs enough identity to accept or reject trusted-phone automation requests.

### Mini Program Local Profile Per Lock

For each remembered lock, the Mini Program stores:

- last successful `deviceId`
- last device name
- local `clientId`
- optional saved PIN
- `autoConnect` switch
- `autoAuth` switch
- `proximityUnlock` switch
- local RSSI threshold
- local nickname for this phone on this lock

### Binding Flow

1. A phone connects over BLE.
2. The user performs manual PIN auth.
3. The app sends a bind request with its generated `clientId` and nickname.
4. Firmware allocates a trusted-phone slot if space exists.
5. Firmware persists the trusted-phone record.
6. The app persists local remembered settings for that lock.

### Unbinding and Revocation

- An admin user may remove a single trusted phone.
- An admin user may clear all trusted phones.
- Removing a trusted phone revokes automatic convenience flows for that `clientId`.
- If the user wants to revoke **all** access from a removed phone, the user must also change the global PIN.

This revocation rule is intentional and explicit in the product model.

## Authentication and Authorization Model

### Manual Auth

Manual auth remains available for temporary use:

- command requires only the current global PIN,
- success grants a short auth window,
- lock/unlock commands are allowed during that window.

### Trusted Auto Auth

Trusted automatic flows use a separate trusted-phone auth command:

- the command includes `clientId` and PIN,
- firmware checks that the `clientId` exists in the trusted-phone list,
- firmware checks that the PIN matches,
- success grants the same short auth window.

This split is what lets the product support both temporary manual use and revocable automatic convenience.

### Authorization Window

- Successful auth grants `30 seconds`.
- A new successful auth resets the window to `30 seconds`.
- After expiry, the state returns to unauthorized.

### Wrong-PIN Lockout

- Maximum consecutive failures: `5`
- Lockout duration: `60 seconds`
- During lockout, auth attempts are rejected.
- `STATUS` still remains available.

## Proximity Auto Unlock State Machine

### Preconditions

A proximity unlock attempt may start only when all of the following are true:

- BLE is connected,
- the phone is a trusted phone for this lock,
- local `autoConnect` is enabled,
- local `autoAuth` is enabled,
- local `proximityUnlock` is enabled,
- a saved PIN exists locally,
- the lock state is currently `LOCK`,
- no active proximity cooldown is in effect.

### RSSI Gate

The app must not unlock on one strong RSSI sample.

Required rule:

- RSSI must remain above the configured threshold continuously for `2 seconds` before auto-auth begins.

Recommended additional rule:

- use a small rolling sample window so brief spikes do not count as a valid hold.

### Trusted Auto Flow

1. The app reconnects to the remembered device.
2. The app begins observing RSSI.
3. If RSSI satisfies the hold rule, the app sends trusted auto-auth.
4. Only after auth success does the app send `UNLOCK`.
5. Firmware starts relock timing immediately after unlock.

### One-Shot Rule

After one proximity unlock:

- the app must not auto unlock again until the phone has clearly left the proximity zone and re-entered,
- or until a defined cooldown has expired and the state has returned to `LOCK`.

Recommended release rule:

- require RSSI to drop below threshold by a meaningful margin before another automatic attempt is allowed.

### Failure Handling

If any of the following occurs:

- BLE disconnect,
- auth failure,
- auth expired,
- lock state already `UNLOCK`,
- write failure,

then the app must clear the in-flight auto-unlock attempt and wait for a fresh valid proximity cycle.

It must not replay stale unlock commands on reconnect.

## Auto Relock Behavior

### User-visible options

The relock delay is selectable in the Mini Program:

- `3 seconds`
- `5 seconds`
- `8 seconds`
- `10 seconds`

Default:

- `5 seconds`

### Lock behavior

- Any successful unlock starts the relock timer in firmware.
- Manual relock before timer expiry cancels the pending auto relock.
- A second unlock request while already `UNLOCK` must not stack duplicate relock timers.

### Source of truth

Firmware is the source of truth for:

- current lock state,
- current relock delay,
- whether a relock timer is currently armed.

## Recommended Protocol

### Existing commands retained

- `LOCK`
- `UNLOCK`
- `STATUS`
- `A<angle>` as maintenance-only, still auth-gated

### Manual auth command

- `PIN <pin>`

### Trusted automatic auth command

- `TPIN <clientId> <pin>`

`TPIN` is for trusted-phone automation and revocable convenience.

### PIN management

- `PINSET <oldPin> <newPin>`

Rules:

- requires fresh successful auth,
- updates persisted firmware config,
- survives reboot.

### Trusted-phone management

- `BIND <clientId> <nickname>`
- `UNBIND <clientId>`
- `TRUST LIST`

Rules:

- binding requires a fresh successful manual auth,
- duplicate `clientId` updates nickname instead of creating a second row,
- if the list is full, binding fails clearly,
- unbind requires fresh successful auth.

### Relock configuration

- `RELOCK <seconds>`

Valid values:

- `3`
- `5`
- `8`
- `10`

### Response style

Responses should stay short and machine-parseable.

Recommended examples:

- `AUTH OK 30`
- `AUTH FAIL 2`
- `AUTH LOCKED 60`
- `TPIN OK 30`
- `TPIN DENY UNKNOWN_CLIENT`
- `PINSET OK`
- `PINSET FAIL`
- `BIND OK SLOT=2`
- `BIND FAIL FULL`
- `UNBIND OK`
- `RELOCK OK 5`
- `ACTION OK LOCK`
- `ACTION OK UNLOCK`
- `DENY AUTH REQUIRED`
- `DENY AUTH EXPIRED`
- `STATUS LOCK AUTH=0 REL=5 ANGLE=0`
- `STATUS UNLOCK AUTH=1 WINDOW=24 REL=5 ANGLE=180`

The first release should implement these response shapes literally so the Mini Program parser and firmware stay aligned.

## Firmware Persistence Strategy

### Storage approach

Use a small versioned config block in STM32 Flash with:

- magic value,
- struct version,
- sequence number,
- CRC/checksum,
- payload fields.

Recommended robust approach:

- use `2` reserved Flash pages,
- always write the next full config to the inactive page,
- verify checksum,
- on boot, load the highest valid sequence,
- if both copies are invalid, fall back to defaults.

This is safer than a single overwritten page and more tolerant of interrupted writes.

### Persisted fields

At minimum:

- PIN
- relock seconds
- trusted-phone record count
- trusted-phone records

### Safe defaults

If persisted config is invalid:

- PIN falls back to default bootstrap PIN,
- relock seconds falls back to `5`,
- trusted-phone list becomes empty.

The Mini Program should surface that state clearly after reconnect.

### Cross-phone matrix

At minimum verify:

1. Phone A binds successfully.
2. Phone B binds successfully.
3. Phone A auto reconnects and trusted auto-auth works.
4. Phone B auto reconnects and trusted auto-auth works.
5. Removing Phone A does not break Phone B.
6. Removed Phone A can no longer use `TPIN`.
7. Removed Phone A can still use manual `PIN` until the global PIN is changed.

### Proximity matrix

Verify:

1. RSSI spikes alone do not unlock.
2. Continuous RSSI hold unlocks exactly once.
3. Already-unlocked state does not double-trigger.
4. Re-entry after leaving range can trigger again.
5. Disconnect during auto-auth does not replay stale commands.

## Out of Scope

This design intentionally does not include:

- Internet remote unlock,
- backend user accounts,
- cloud audit logs,
- encrypted BLE transport beyond the current module limits,
- biometric verification,
- temporary guest codes with expiry,
- fine-grained user roles.

## Recommendation

Implement this as the product-grade first release baseline:

- keep one global PIN,
- add trusted-phone identity for convenience flows,
- keep manual PIN access for onboarding and temporary use,
- put relock authority and durable config in firmware,
- keep RSSI decisions in the Mini Program with conservative guards,
- validate the cross-phone and persistence behavior before any cosmetic polish.
